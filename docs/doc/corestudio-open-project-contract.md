# CoreStudio 开放项目数据协议

> 所属项目：CoreStudio Desktop
> 日期：2026-09-19
> 状态：基础实现已提交 b959f02e；恢复与冲突处理补齐并通过验证；未安装或发布正式版。
> 来源：外部图片接纳、外部整理排布及项目健壮性的用户讨论，并核对现有读取、接纳和维护代码。

## 1. 目的与适用范围

CoreStudio 项目是用户可以在应用外整理的本地文件夹。用户可以放入图片，也应能通过公开、未加密的整理信息审计和修改顺序、排布。程序必须把文件新增、修改、替换、删除、暂时不可读和数据不一致视为正常输入条件。

项目内受支持的原图，是素材存在与内容的事实来源；索引不能否定一张实际存在的图片。坐标、顺序、标注、生成记录等表达用户组织和使用素材的结果，不能全部从原图推导出来。

本协议是后续文件读取、保存、自动接纳、项目维护和外部整理功能的共同约束。本轮实施统一项目文件、外部排布同步、恢复与目录改名跟随。协议同时约束后续迭代；全种类外部修改的自动修复不因本轮实施而被视为已经完成，实际能力与验证见第 12 节。

## 2. 必须保持的原则

1. **文件可变，项目可维护。** 所有持久化数据都可能被外部修改或丢失；任何解析或关联失败都必须有受控的失败路径，不能让应用崩溃或让项目失去检查、修复入口。
2. **局部问题局部隔离。** 一张坏图、一条坏记录不阻塞无关素材的读取和操作。只有确实依赖异常数据的操作才暂停。
3. **可读与可写分别判断。** 能展示可恢复内容，不等于可以覆盖损坏的文件。不能把空对象、降级场景或不完整索引当作完整项目自动保存。
4. **结果随项目走。** 顺序和排布结果保存在项目内，公开可读、可编辑；自动排布规则只产生新结果，不在每次打开时重新解释并改写已有结果。
5. **文件少，职责清楚。** 项目数据按领域组织在文件内部，不按每个功能、处理阶段或异常情况新增文件。不增加整理历史系统；已有事务恢复设施可以复用，但不能成为第二份长期业务记录。文件数量不能随素材数或功能数线性增长，健壮性由校验、统一保存和恢复规则保证。
6. **恢复有依据。** 自动补齐只恢复能够确定的信息；无法确定的保留为缺失或冲突，不猜测生成参数、旧坐标或用户意图。
7. **读取收敛，写入保守。** 重复核对、重启、漏事件后的补扫不重复添加素材，不复活明确移除的元素，不覆盖尚未处理的外部修改。

## 3. 每种数据表达什么

这里区分数据职责，不要求新增对应文件或数据库。

| 数据 | 表达的事实或结果 | 丢失时的恢复边界 |
| --- | --- | --- |
| 项目原图 | 素材内容、可读性、格式、尺寸 | 有其他已核实的完整副本才能恢复原图；缩略图不等于原图 |
| 图片索引与路径关联 | 原图与素材 ID、画布引用的关系 | 扫描原图，并结合仍有效的关联重建；不能仅凭文件名认定身份 |
| 顺序与排布信息 | 当前整理顺序、元素位置和明确的放置状态 | 优先使用原生场景与其他仍有效记录；缺少的结果才重新生成 |
| 原生 Excalidraw 场景 | 完整元素、坐标、文字、连线、分组等 | 保持原生保存；图片和排布文件不能恢复丢失的全部非图片内容 |
| 接纳处理状态 | 已处理、待处理、失败和主动移除等当前状态 | 核对原图、索引和场景后恢复；丢失不能直接等同“所有图片都是新图” |
| 缩略图、预览缓存 | 可替换的显示数据 | 由可读原图重新生成，不参与决定素材是否存在 |
| 项目清单、生成记录 | 项目身份、设置、来源和生成信息 | 只补可证明的部分；不伪造身份、提示词或模型来源 |

“项目文件夹里的图片”沿用既有正式原图和扫描范围：根目录、普通子目录、受支持的资产位置；缓存、导出、备份、内部工作目录、嵌套项目和越界路径不作为新素材。普通目录就地登记、根目录 `inbox/` 复制入库的现有区别仍保留。不能因开放项目而把缓存或导出图重新接纳。

## 4. 文件、素材与画布元素的关系

- 路径用于定位，不独自决定身份；同一路径可能被替换，不同路径也可能有相同内容。
- 素材 ID 与画布元素 ID 分别表达素材和一次放置，同一素材可能被放置多次。外部排布必须绑定元素身份，不能按数组下标或文件名随意匹配。
- 重命名或移动时，只有内容与已有关系足以确定对应，才自动更新引用；有歧义就保留待处理状态，不能随机绑定。
- 原图被同名替换时必须重新验证内容与缓存，不沿用旧尺寸、旧缩略图或未经核实的生成来源。是否延续旧素材身份列入技术设计，不能把替换悄悄当成普通新增。
- 从画布移除不等于删除原图。有效的主动移除信息必须阻止自动补回；删除排布记录也不表示删除原图或画布元素。
- 主动移除与放置状态属于当前结果，不是操作历史。若所有表达移除意图的数据都丢失，程序无法准确推断原意；已知存在歧义的资产先列为待放置，不批量复活。正常新图片仍按自动接纳规则处理。

### 项目文件夹改名

- 正在打开的项目在同父目录内改名时，按项目 ID 和本次运行取得的目录身份确认后自动跟随，保留未保存编辑、画布及 Agent 绑定。确认前暂停相关磁盘写入，不在旧路径重新创建项目目录。
- 最近项目只按记录的位置和项目 ID 重新打开，不扫描附近的同 ID 文件夹猜测改名。项目关闭期间改名或移动后，通过“打开项目”重新选择文件夹；这是避免误开备份的有意取舍，不要求恢复旧名称。
- 原文件夹仍在但项目身份暂时不可读时，保留最近项目记录，提示稍后重试或从“打开项目”检查。项目文件修好后可重新打开，不把 JSON 损坏或缺失误当成文件夹改名，也不覆盖原件。
- `stat.dev` 设备编号可能随重启或重新挂载变化，不能作为跨运行的身份依据。最近项目不再保存目录编号，旧记录中的 `directoryId` 不参与重开校验；运行中的目录替换检测仍使用实时取得的设备和目录编号。
- 运行中无法确认改名、发现重复 ID、目录身份不符或租约冲突时，不猜测绑定。原路径及项目 ID 仍匹配时，其他位置存在副本不阻止打开该明确路径。文件夹名和项目显示名称分别处理，不隐式改写项目名称。

## 5. 外部整理与 Excalidraw 的结合

### 5.1 保存与职责

**已确认的简化方案：** 保留完整的 `scene.excalidraw.json`，把 CoreStudio 自有的长期信息收敛到一份公开、未加密的 `project.json`。上一版单独新增 `layout.json` 的建议由此替换；排布依然与原生场景分离，但不再与素材记录、项目身份等自有信息拆成多个文件。

本轮 v2 项目目录结构：

```text
项目文件夹/
├── project.json             # 项目说明、素材记录、顺序和排布等当前结果
├── scene.excalidraw.json    # 完整原生画布
├── assets/                 # 应用管理的原图
├── 用户自己的图片或目录     # 沿用现有目录范围，不强制搬入 assets
└── cache/                  # 可重建缓存及现有短期恢复工作区
```

`project.json` 内按项目、素材、画布放置等领域分区：项目身份与设置；按素材 ID 组织的路径、尺寸、来源和生成信息；按元素 ID 组织的素材引用、坐标和放置状态；明确的整理顺序。字段可以丰富，但同一事实在这份文件里只保留一处，其他地方使用 ID 引用。格式版本用于兼容判断，不是历史版本。本轮字段与外部编辑约定见第 12 节。

接纳完成后的素材信息、位置及主动移除状态归入上述当前记录，不再长期保存一份带完整图片记录和元素快照的独立接纳账本。重试计数、扫描游标等可重算状态优先留在内存；确需跨重启恢复的未完成操作复用短期恢复设施，完成后清理，不持续累积。

缓存和临时恢复数据可以有多个内部文件，但必须有用途、生命周期和清理规则，不散落在项目根目录。缓存丢失可以重建；仍在提交中的恢复记录须先核对再清理，不能把整个内部工作区当成随时可删的纯缓存。维护时按需产生的备份也不作为日常结果的一层，不另加持续快照系统。

统一项目文件与原生场景保留必要的坐标重复，以满足原生保存和回退要求；由同一适配桥管理同步，不能再引入第三份长期位置记录。文件增大本身不是拆分理由；图片二进制不嵌入 JSON。只有真实的读写或编辑性能证据才能推动后续调整，不能预先按图片逐个生成附加文件。

旧 v1 项目打开时迁移：先合并、核验并原子发布 v2，再删除内容仍与迁移输入一致的旧 `image-records.json`、`image-intake.json`。中断后只清理与新分区内容相同的遗留副本；外部已经修改或损坏的旧文件保留。迁移失败保留原件，不继续双写。

CoreStudio 的项目适配桥负责读取、核对并向现有项目房间提交有效变更，再向 Excalidraw 提供普通场景元素。这里的“桥”是数据适配职责，不新增一个绕过项目房间的磁盘写入者，也不要求改造 Excalidraw 的坐标、交互和撤销底座。

用户在画布上移动、缩放、旋转或手动整理后，同步更新原生保存与公开结果。外部修改经接纳后走相同路径。两份文件不能各自运行独立保存循环；部分保存失败必须可检测，不能报告全部成功。

### 5.2 读取和合并

以下“整理信息”指统一项目文件中的整理部分。整份文件无法解析时，不能假装还能逐条读取：使用原生场景或本次运行最后一次有效结果，保留坏文件并提供修复入口；JSON 可解析但部分字段有错时，才逐项隔离。项目身份缺失时，恢复阅读与正式协作写入分别处理。

- 首次打开：读取原生场景，再将当前项目中身份匹配、格式有效且没有冲突的整理结果应用到对应元素；未覆盖的元素沿用原生值。
- 整理信息缺失、为空：使用原生结果，经核对后补建；不先执行全局重排。
- 整理信息部分记录缺失：保留有效记录，只补缺项；删除条目不表示移除图片。
- 整理信息损坏或来自无法识别的未来格式：原生可用时继续使用原生；保留外部文件并报告，不能自动写回覆盖。
- 项目已经打开时读取失败：继续保留最后一次有效的画布，不突然跳回磁盘上的旧坐标。
- 原生场景也不可读：以原图和有效附加信息提供恢复视图及维护入口，明确哪些内容未恢复；不能把恢复视图自动覆盖到损坏的原生文件。
- 同时修改原生与附加信息：不能仅按修改时间或“附加文件永远优先”判胜；比较共同基线和字段变化，互不冲突的变更合并，同一元素同一字段冲突保留双方结果供选择。

### 5.3 排序与排布

首次接纳仍按同次发现的创建时间、相对路径确定顺序，创建时间不可用时使用首次发现时间；后发现的图片追加，不插队。创建时间是初始排序依据，不保证等于加入文件夹的时间。已有显式整理顺序优先，不能被文件时间重新计算覆盖。

沿用横向利用宽度、到边界向下换行的规则。当前源码默认宽度 6940、间距 60，约容纳 10 张宽 640 的横图；这是默认规则，不是对所有图片按张数强制换行。后台处理批次不决定换行，已有元素不因新图到达或视口变化重排。

结果文件中的顺序与坐标分别具有明确含义：修改坐标直接改变位置；仅修改顺序不隐式全局重排，整体排布由用户显式触发。Excalidraw 元素层叠顺序不能冒充素材整理顺序。后续追加依据已接纳的当前整理结果延续，不再把接纳 ledger 的历史落点当作独立排布权威；具体追加游标与手动整理后的边界算法在技术设计中定义。

## 6. 统一核对与外部变化同步

打开项目、文件变化、应用恢复或重新获得焦点、应用自身写入前，以及手动检查与修复，都复用同一套事实核对和问题分类。日常增量核对与完整维护可有不同扫描成本，不能有相反的数据判断。

推荐处理顺序：发现变化 → 等待稳定 → 读取与校验 → 与已接纳基线比较 → 应用无冲突变化 → 保存需要补齐的结果 → 报告剩余问题。

- 监听兼容原地修改和临时文件改名替换；以目录补扫处理漏事件，不能只依赖某一个文件句柄。
- 合并短时间连续事件，初始建议静默 300–500 毫秒再读；时间只是调度参数，仍需校验完整性与读取期间是否变化。
- 内容未变不重复应用；记录本次自身写入的内容指纹，避免监听与保存形成循环。
- 拖拽或编辑期间不突然覆盖正在操作的元素；结束后基于变化比较合并，无关元素可正常同步，同字段冲突不能按最后到达顺序静默覆盖。
- 只应用受影响的元素和字段，保持无关内容、选区、视口与正常撤销行为。外部整理作为可识别的编辑操作进入现有协调机制，撤销不得回滚后来发生的无关修改。
- 自身写入前检查磁盘是否偏离读取基线；单文件使用原子替换，跨文件保存复用现有协调与恢复能力。外部编辑器不会遵守应用租约，不能把租约当作外部文件不会变化的证明。
- 冲突或权限错误只暂停依赖该数据的落盘，清楚显示未保存状态并保留恢复、导出当前结果的入口；不得默默丢弃内存中的编辑。

## 7. 异常、恢复与删除合同

| 情况 | 继续使用 | 自动处理 | 不允许的行为 |
| --- | --- | --- | --- |
| 新原图存在、索引无记录 | 其他素材正常 | 验证图片、核对已有引用与移除状态后登记 | 索引缺项导致整项目打不开，或重复制造元素 |
| 单张图片损坏或正在复制 | 其他素材正常，该图占位或等待 | 稳定后重试；持续失败进入可定位的问题报告 | 中断整批、无限忙等 |
| 图片路径暂时消失 | 保留已有位置与缺失状态 | 稳定核对、查找项目内可确定的移动关系；回来后恢复 | 一次删除事件就清空关联和坐标 |
| 原图确认丢失 | 保留缺失标记，其他内容可编辑 | 有已核实的完整副本才恢复 | 用缩略图伪装原图、删除无关记录 |
| 索引一条错误 | 加载有效条目 | 隔离坏项，能从事实确定的字段可补齐 | 将坏项传播为整个索引不可用 |
| 索引整体缺失或损坏 | 扫描原图，使用有效场景与整理记录提供恢复入口 | 缺失时可确定性补建；损坏原件保留，重建替换须显式执行 | 自动保存空索引、捏造来源信息 |
| 整理信息缺失或局部缺项 | 原生结果兜底 | 经稳定性和并发检查后从有效结果补建 | 重新运行算法移动全部旧图 |
| 整理信息格式错误 | 使用最后有效结果或原生结果 | 文件修好后重新核对 | 覆盖外部文件、删除其未理解内容 |
| 项目清单或原生场景损坏 | 保留素材访问、诊断和恢复入口 | 恢复已核实信息；身份不确定时暂停相关协作写入 | 伪造空场景覆盖原件，静默更换项目身份 |
| 未识别的格式版本或字段 | 能理解的内容尽量读取 | 保留未知信息；无法无损往返时暂停受影响文件写入 | 降版本覆盖、丢弃未知字段 |
| 所有整理信息丢失，但图片仍在 | 能重建一个可使用的素材项目 | 重新识别、建立基础记录和默认排布，并说明信息损失 | 声称恢复了原顺序、原坐标、标注或生成历史 |

自动补建缺失文件前，应确认其仍缺失、当前项目身份可信且没有正在进行的外部替换；不能让重建与编辑器持续争抢同一文件。损坏文件的显式替换复用已有维护备份能力，不新增常驻历史系统。

健康报告必须指出文件或元素、问题类型、受影响能力和可用修复动作。正常同步保持安静，持久失败可发现，不连续弹窗。文件被修正后无需重启应用即可重新核对。

## 8. 开放边界与现有协作协议

文件管理器、编辑器和外部采集工具是正常的项目使用入口。开放意味着程序对任意文件变化都要能容错，不意味着所有内部文件都已经是稳定的外部编辑 API，也不意味着非法路径、不可理解版本或身份冲突可以绕过校验。

此次对外整理入口是公开项目文件中的顺序与排布信息；原生场景保留原生保存能力。内部事务文件、运行时租约与授权数据不作为整理接口。所有位置仍遵守项目目录边界及既有图片格式协议。

已有 Agent 工作流继续优先使用 CLI / Local Bridge。新增外部整理入口由同一个项目适配与协调机制接纳，不把“外部修改可能发生”误写为“所有 Agent 默认可以直接改内部文件”。具体工具能否直接编辑公开文件，仍遵循用户授权和该入口的发布合同。

## 10. 验收合同

7. 正在拖动与外部同时修改同一元素，或外部同时修改原生与整理信息，不静默覆盖；无关元素修改可以合并。
8. 自身保存触发的监听不产生回环；保存中断或一份文件写入失败可检测、可继续恢复，不误报成功。
9. 未知版本、权限不足、单张坏图、无效坐标均局部降级；问题可定位、可修正，相关写入暂停时无关工作不被阻断。
10. 非图片元素、软删除、多次放置同一素材、撤销/重做、CLI 与 Agent Board 协作仍遵守现有合同。
11. 移动整个项目文件夹后，图片、结果和关联仍可使用；不依赖原机器的绝对路径或应用外索引。
12. 增加图片与整理功能不会新增根目录业务文件或每图附加文件；未完成恢复任务结束后清理，已接纳数据不在多份长期账本中重复保存。统一格式迁移需验证老项目可读、数据完整及不持续双写。
13. 在原父目录内给项目文件夹改名：打开中的项目确认身份后自动更新路径并继续保存，未保存编辑不丢失；关闭期间改名后，最近项目提示通过“打开项目”重新选择。运行中重复 ID、目录身份不符、目标租约冲突或无法定位时不误绑定，不在旧路径创建目录。

### v2 字段与外部编辑约定

**Agent 整理已有图片的补充约定（Skill 26）：** 公开 `layout.order` 是整理结果，不是添加时间证明；`imageRecords.createdAt` 可能由导入批次共用。要求按时间重排时先沿用用户已确认的依据，按原图路径核实文件创建时间或可靠的逐图接纳证据。只有用户选择创建时间时才以 birth time 升序、同时间按文件名及相对路径排序；不能把该结果称为已恢复真实添加历史。顺序与可见排布都要改变时，一起修改公开顺序和坐标。项目绑定、能力、场景读取及存储状态正常后才可执行公开文件整理，写前核对最新快照，写后以同一依据验证 Room、公开结果和原生保存。此流程不改变后台追加规则，也不是 CLI 失败后的覆盖手段。

顶层保留 `projectId`、`name`、版本及项目设置，增加三个分区：

| 分区 | 内容与用途 |
| --- | --- |
| `imageRecords` | 以素材 `fileId` 为键，存原图相对路径、尺寸、内容指纹及已有来源信息。 |
| `layout.order` | 图片元素 ID 的当前整理顺序。修改顺序会保留；不改变 Excalidraw 层叠顺序，也不隐式重排坐标。 |
| `layout.elements` | 以元素 ID 为键，存 `x / y / width / height / angle`、素材引用和原生删除状态。外部坐标修改是本轮支持的同步入口。 |
| `layout.sceneHash` | 两份文件最近完成同步时的原生场景基线，由程序维护，不作为排序字段。 |
| `intake` | 当前接纳与重试状态。接纳完成条目只引用素材和元素 ID，未完成条目保留提交所需内容；不再重复长期保存完整元素和素材记录。 |

例如，只移动一张图时，编辑 `layout.elements[元素ID].x` 和 `.y` 即可。宽高必须是有限的非负数，角度使用原生弧度；素材和元素 ID 用于关联，不用文件名或数组位置替代。`isDeleted` 本轮作为原生删除状态的镜像，删除操作仍通过画布完成，删除一条公开记录只会触发补建。

后台每秒核对两个业务文件的目录项签名，没有变化时不读全量 JSON；本地连续编辑后留出至少 500ms 安静窗口。发现有效变更通过 Room 合并和持久化；坏记录保留、提示并跳过。程序继续正常显示最后有效画布；相关保存受阻时不能把内存内容当作已保存。

普通保存使用单一的项目文档写入队列，保留无关分区和未知字段。两份业务文件需要一起变化时，短暂写入 `cache/scene-commit.json`，包含本次未完成提交的前后内容；完成核验后立即删除。中断重开后，仅当磁盘仍对应这次提交的前后版本时继续；发现外部第三种内容就保留恢复记录并报告冲突。它不是历史文件，缓存清理不会删除它。

### 已知边界

- 外部同时重写原生场景和公开排布，或同一坐标与本地编辑冲突时，保留双方并暂停相关保存。错误提示中的“处理文件变化”展示差异数量和最多 8 项摘要，可以保留当前画布、采用整理文件，或在原生文件不同的情况下采用原生画布；选择应用到整个画布，不是逐元素合并编辑器。
- 两份业务文件都不可用且原生关联也不可读时，打开文件夹会预览可恢复原图并提供显式重建；按创建时间生成默认位置、创建新的项目身份。不能还原旧坐标、文字、连线、删除意图或生成参数，旧 Agent 连接需重新绑定。若项目窗口仍开着，可从当前内存画布恢复文件并保留项目 ID。
- 外部替换、移动原图沿用已有接纳与健康检查规则；有歧义的关联不会自动猜测。本轮不把所有索引字段的外部修改都定义为实时编辑接口。
- 图像实际容量取决于原图尺寸、解码和视口工作量；元数据规模通过不能替代照片和高分辨率图片的压力验收。

### 最近项目跨重启识别修复（2026-09-20）

旧实现把持久化的 `stat.dev:stat.ino` 用作最近项目重开的硬条件，设备编号变化时，即使文件夹仍在，也会误报无法确认改名项目。现按第 4 节处理：最近项目只认原位置和项目 ID，历史设备编号不参与校验；运行中的改名跟随保留原有目录身份和租约保护。新记录不保存设备编号；父目录别名按真实路径去重，不合并不同位置的同 ID 副本。

复查发现“附近只有一个同 ID 候选”仍可能是备份，尤其在原项目 JSON 暂时不可读或项目移到其他父目录时。因此取消最近项目的自动候选扫描，未增加持久身份系统。原位置不可用或被其他项目占用时要求显式重新定位；原文件夹仍在但身份不可读时保留原记录和原件，提示重试或检查。本轮采用简化实现，代价是关闭期间改名需要重新选择文件夹。

验证：先以失败测试复现误开备份，修复后 4 个文件共 52 项定向测试与类型检查通过，覆盖损坏、缺失及无 ID 的清单与同 ID 备份共存、原项目跨父目录移动后留下备份、原文件修复后重新打开，以及运行中改名后继续保存。固定 SOURCE DEV 实际点击验证两种错误分别提示且保留原记录，修好测试清单后无需重启即可打开原画布；旧设备编号不再阻止打开。验收实例正常退出，进程及端口无残留，开发版最近项目列表已还原。没有重启机器，未安装或发布。

提示收口：项目错误展示复用统一格式化入口，去除 Electron 的远程方法前缀及内部缺失标记，空原因使用本地化兜底；读取失败和重新定位文案缩短为一条操作提示。原始错误及原因仍留在主进程日志，不新增弹窗或提示入口。新增失败测试后，格式化、首页重试和最近项目共 60 项测试通过，类型检查通过；固定 SOURCE DEV 界面确认仅显示中文提示，验收实例及临时文件已清理、开发版项目列表已还原。未安装或发布。

### 补齐的恢复与冲突处理（2026-09-19）

- 公开结果与原生画布仍是两份业务文件，不增加日常历史层。显式修复沿用 `exports/maintenance-backups/`，只在用户做出恢复或冲突处理选择时产生备份，包含磁盘原件、当前未保存画布以及存在的未完成提交记录。
- 选择前预览，选择后重新核对画布序列、路径、业务文件和待提交记录。后台 `intake` 重试计数和 `updatedAt` 的变化不会使位置选择过期，提交时保留这些最新字段；素材记录、设置或画布发生变化则停止这次选择。未完成提交的替换也进入同一文档写入锁，不能清除后来出现的提交。
