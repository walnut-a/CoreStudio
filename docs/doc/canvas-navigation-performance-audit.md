## 初始诊断结论与证据边界

用户反馈同一项目画廊流畅、画布明显卡顿，具体发生在平移与缩放。截图缩放为 5%，大量图片同时出现在视口内。这类场景需要同时控制每次导航的业务计算、可见图片绘制成本和高清资源驻留，不能只增加“视口外不画”这一层优化。

当前实现已经具备画廊窗口化、画布视口裁剪、单元素栅格缓存、连续缩放期间复用缓存，以及缩略图/预览图/原图分级加载。建议先剥离纯导航中的无关工作、复用小地图底图，再完善图片缓存的降级和回收；只有帧分析证明逐图绘制仍占主要时间时，才引入总览瓦片缓存。

这些是从代码确认的优化机会，尚未取得现场性能录制，不能断言某个函数就是这次卡顿的唯一根因，也没有量化加速倍数。

## 优化前已确认的实现与问题

### 1. 画廊与画布的工作量不同

[ImageBrowseView.tsx](../../excalidraw/apps/image-board-desktop/src/app/components/ImageBrowseView.tsx) 第 728–739 行根据可见窗口截取 `visibleItems`，第 858 行只挂载该范围的图片卡片，缩略图请求也按可见图片触发。

[Renderer.ts](../../excalidraw/packages/excalidraw/scene/Renderer.ts) 第 159–225 行把元素索引构建和可见性查询放在同一个 memo 中，缓存键含滚动位置和倍率。即便元素完全没变，移动视口也会重建全场景 `Map`，再逐个判断是否可见。

[staticScene.ts](../../excalidraw/packages/excalidraw/renderer/staticScene.ts) 第 307 行起逐个绘制所有可见元素。在截图这种低倍率总览中，可见元素本身很多，视口裁剪能剔除的比例有限。提高查询效率不能消除这些可见图片的绘制成本。

建议：先将“由场景内容决定的元素索引”和“由视口决定的可见集合”分开缓存。只有基准证明查询仍占明显时间，再增量维护空间索引；无需一开始就引入四叉树。

### 2. 纯导航仍进入业务变化链路

[上游 App.tsx](../../excalidraw/packages/excalidraw/components/App.tsx) 第 4276 行在更新后触发 `onChange`；[桌面 App.tsx](../../excalidraw/apps/image-board-desktop/src/app/App.tsx) 第 2090 行起没有先将纯视口变化与内容变化分离。

因此纯平移也会进入：

- 生成任务与场景的对账：[pendingGenerationSceneReconciliation.ts](../../excalidraw/apps/image-board-desktop/src/app/pendingGenerationSceneReconciliation.ts) 第 27 行即构建全量存活元素集合，即使当前没有生成任务。
- 图片 ID 汇总：[sceneImageFileIds.ts](../../excalidraw/apps/image-board-desktop/src/app/sceneImageFileIds.ts) 先收集再比较，返回相同数组只避免状态变化，不能避免前面的计算。
- 选区、属性栏和图片加载调度：[canvasSceneChangeRendererController.ts](../../excalidraw/apps/image-board-desktop/src/app/canvasSceneChangeRendererController.ts) 第 110 行起。空选区已有快速返回，不能把这一分支描述为必然进行全量选区扫描。
- 房间增量检查：[projectRoomClientController.ts](../../excalidraw/apps/image-board-desktop/src/app/projectRoomClientController.ts) 第 303 行起重建当前元素 Map，再过滤变化元素。没有元素或共享配置变化会返回，不代表每次平移都保存磁盘或发送完整场景。

建议按元素版本、选区、文件版本、共享配置与视口分别判定失效。纯导航只更新视口、必要绘制与可见图片调度；空生成任务直接跳过对账，图片列表和房间差异检查只在对应内容变化时执行。版本判定必须使用可靠的场景修订号或不可变引用合同，不能假设任意数组引用相同就一定没变。

### 3. 小地图缓存了几何，但没缓存场景底图

[CanvasMinimap.tsx](../../excalidraw/apps/image-board-desktop/src/app/components/CanvasMinimap.tsx) 第 208–209 行同时订阅内容变化和滚动变化，通过同一个 RAF 合并绘制。这能合并同帧重复通知，不能消除每次导航的绘制。

[canvasMinimapRenderer.ts](../../excalidraw/apps/image-board-desktop/src/app/canvasMinimapRenderer.ts) 第 34、96 行复用元素边界，但仍遍历、创建数组和对象；[canvasMinimapCore.mjs](../../excalidraw/apps/image-board-desktop/src/app/canvasMinimapCore.mjs) 第 177 行起重新汇总内容范围、读取样式，再绘制全场景简化矩形。小地图没有解码原图，其开销不应与主画布图片解码混为一谈。

建议拆成内容底图、选区层和视口框。内容、主题、尺寸和映射变换不变时复用底图，平移只更新视口框；缓存内容范围及主题颜色。

边界：当前地图范围由内容与视口的并集决定。视口移出原有范围、导致映射变换改变时必须重建底图，不能为了缓存静默改变自动包含视口的导航行为。

收益尚未量化，小地图只能列为可独立 A/B 的优化项，不能凭截图把它认定为主要瓶颈。

### 4. 图片分级加载只有升级，没有导航驱动的降级

[projectFs.ts](../../excalidraw/apps/image-board-desktop/electron/projectFs.ts) 第 122–123 行定义 320px 缩略图、1280px 预览图。[imageRenditions.ts](../../excalidraw/apps/image-board-desktop/src/app/imageRenditions.ts) 当前以屏幕尺寸决定升级：180 CSS px 起请求 preview，720 CSS px 或 1400 物理 px 起请求 original，并在导航停止约 220ms 后调度。

同文件第 126 行起，只要原图已经加载或正在加载，就跳过后续较低等级请求。[imageRenditionLoadPlan.ts](../../excalidraw/apps/image-board-desktop/src/app/imageRenditionLoadPlan.ts) 的加载状态为累加式集合，当前导航链路没有按倍率回退、离屏释放或按解码字节预算驱逐的流程。图片通过 `replaceFiles` 进入编辑器的文件与图片缓存，因此不能只清空“已加载 ID”集合就当作已释放资源。

纯函数探测使用一个 1200×1200 场景单位的合成图片，DPR=2，结果如下。这是调度行为验证，不是真实项目内存或帧率测试。

| 状态 | 请求 |
| --- | --- |
| 初次处于 5% | 无升级请求，依赖已有低清资源 |
| 初次处于 20% | preview |
| 初次处于 100% | original |
| 原图已加载，缩回 5% 或 20% | 无请求，不安排降级 |

这可能解释“浏览一阵、看过大图再缩回总览后更卡”，但用户尚未明确反馈这种时间趋势，现场占比需要验证。不能据此声称 5% 时全部图片都首次加载原图。

建议让显示缓存支持双向等级选择，按屏幕物理尺寸选资源；为解码图片与元素栅格缓存共同设字节预算，以最近使用情况回收离屏高清资源。加滞回区间和空闲调度，避免临界倍率反复切换。视需求增加 64/128px 小图级别，不应不经测量就批量生成所有尺寸。

原图仍是导出、参考图和编辑操作的事实来源。显示资源降级不能改变原图、fileId、裁剪坐标、撤销历史或房间内容版本。被裁剪、编辑或当前任务使用的资源需要固定；异步加载完成时再次核对项目、资源修订和当前需求，避免已经缩回去后又被迟到的原图请求升级。

### 5. 连续缩放已有缓存复用，停手后存在集中重建路径

[上游 App.tsx](../../excalidraw/packages/excalidraw/components/App.tsx) 第 13747 行在滚轮缩放时设置 `shouldCacheIgnoreZoom`，第 13846 行在 300ms 后恢复。[renderElement.ts](../../excalidraw/packages/element/src/renderElement.ts) 第 539 行起在倍率不同且不忽略倍率时重新生成元素 Canvas。

因此“滚轮每动一下就把所有图重新解码一遍”不符合代码。实际风险是导航结束时，可见元素的倍率缓存集中失效，以及新进入视口的元素需要创建缓存。平移时已有有效缓存仍被复用，但仍需逐图合成到主画布。

建议录制时单独看停手后的 0–500ms。如果证实存在重建尖峰，按帧预算分批更新清晰缓存、优先处理当前关注区域，并保留旧缓存直到新缓存就绪；也可采用离散倍率档位减少微小倍率差造成的重建。

## 优化顺序

| 顺序 | 工作 | 目标与成本 |
| --- | --- | --- |
| 先取基线 | 在匹配版本的固定开发入口记录平移、缩放与停手阶段的帧时间、热点、可见数及缓存规模 | 明确 CPU、绘制、内存或资源加载谁占主要时间，避免凭遍历次数判断严重程度 |
| 第一批 | 纯导航快速路径；元素索引独立缓存；小地图底图复用 | 低至中等成本，减少与内容总量相关的重复计算，保持现有编辑行为 |
| 第二批 | 图片双向分级、按字节回收、缩放后分帧重建；收窄并限制高清预取 | 中等成本，控制浏览后的内存增长与停手尖峰 |
| 有数据再做 | 低倍率总览瓦片或分块合成缓存，交互期间复用并平移/缩放已有栅格，空闲更新 | 中高成本；针对大量图片同时可见时的逐图绘制。须保持透明叠加、图层顺序、裁剪和选中元素正确 |

初次诊断时，高清预取每侧扩展一个视口，相当于覆盖宽高各三倍、面积九倍的区域；不是必然请求九倍图片，还受到图片大小、分布和已加载状态限制。第二批可改为按方向和屏幕距离优先的小范围预取，设定读取/解码并发与字节预算。

不建议第一轮整体迁移 WebGL/WebGPU、重写画布或要求用户拆散项目。空间索引也不能解决低倍率下本来就全部可见的图片绘制问题；上述更大改造应以性能录制为依据。

## 验证方法与验收边界

实现前固定应用版本、窗口尺寸、DPR、图片集合、初始视口与缓存冷热状态。先用同等规模的合成图片夹具，获得绑定后再复核真实项目；不能把合成夹具结果当作用户项目结论。

覆盖 5%、10%、25%、100% 倍率下的空白平移与连续缩放；区分手势期间和停手后的卡顿。补充“打开项目直接总览”与“多次放大看图后回到总览”、小地图开/关、纯平移与选中图片后平移的对比。

记录帧间隔 P50/P95、超过 50ms 的长任务、主场景绘制与缓存重建时间、业务 onChange 时间、小地图时间、资源读取/解码批次、renderer/进程内存及估算的解码字节。JS heap 不能代替 GPU 和原生图片内存统计。

60Hz 设备以尽量落在 16.7ms 帧预算内为方向，但具体验收阈值需要基线确定；本轮不承诺任意图片数量下固定 60fps。

自动化回归应先验证：纯视口变化不触发内容对账和房间差异扫描；同场景导航复用索引与小地图底图；缩小后出现预期降级/回收且原图不变；异步结果不跨项目、不覆盖较新资源。复杂缓存改动还要覆盖裁剪、旋转、透明图、撤销重做、远端图片更新与选中元素层次。

真实桌面平移、缩放及资源内存验收属于 L3，应使用 `corepack yarn dev:desktop` 的固定身份，遵守已有实例校验与精确进程收尾规范。普通性能代码修改不默认升级到打包。初始诊断没有启动 GUI；后续实现验收使用独立开发项目，详见下文。

## 第一批实现与验证（2026-10-08，底层部分已撤回）

实现边界：

1. 编辑器 API 新增只读 `getSceneNonce()`，使用现有 Scene 更新标识，覆盖数组或元素原地修改。宿主在 nonce、资源/项目/任务依赖不变且 AppState 仅有视口字段变化时，跳过生成任务对账、图片 ID 汇总、选区计算及房间内容差异检查；仍更新最新视口、可见资源调度和 Agent 视口状态。
2. 渲染器把内容索引缓存与可见元素查询分开；平移、缩放只重新计算可见集。场景修改、删除、撤销、绘制中元素和文本编辑会使相应缓存失效。
3. 小地图按场景 nonce 与选区缓存几何及内容范围，按主题、尺寸、DPR 和映射变换缓存底图；保持原有内容与视口并集语义，范围扩张时重新生成底图。

### 实现范围

- 已裁剪图片按保存的 crop.naturalWidth/naturalHeight 选择匹配的现有显示等级，活动裁剪尚未形成 crop 时保持当前等级；同一 fileId 的其他副本也遵守该约束。裁剪像素尺寸不匹配的返回结果不会应用。打开项目时过滤不匹配的缩略图，等待匹配等级；不改元素坐标、文件 ID 或撤销记录。
- 删除中的图片及已离开场景的高清文件采用保留策略，避免替换像素后影响编辑器既有撤销缓存。对此类文件不宣称主动内存回收；裁剪图、删除历史和全部缩略图可使显示源软预算超额。

不再包含：Excalidraw 元素索引缓存、内部图片位图的分帧重建、64 MiB 位图预算、内部缓存失效扩展，以及底层跨分辨率裁剪适配。停止缩放后的集中重建、可见图片逐项合成和内部缓存释放仍由原有内核负责；本版不复用前两批核心补丁的性能结论，也不声称所有瓶颈已经消除。PNG 复制与生成参考图继续使用项目原有出口，本轮未修改这些出口或将原有裁剪导出边界扩大为已验证的新能力。
