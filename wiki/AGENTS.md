# CoreStudio Wiki 维护协议

本文件是 `wiki/` 的 schema。任何 Agent 在创建、更新、查询或体检本 Wiki 前，都必须先读本文件和 [`index.md`](index.md)。

仓库根目录的 `AGENTS.md` 继续生效；发生冲突时，以根目录规则和用户当前明确要求为准。

## 1. 所有权与写入边界

- 仓库已有代码、测试、文档、规格、计划和 Git 历史属于**来源层**。维护 Wiki 时只读，不得顺手改写、移动或“清理”。
- `wiki/raw/` 保存人工明确交付给 Wiki 的不可变快照。摄取后不得原地润色；新版本以新文件加入。
- `wiki/pages/`、`overview.md`、`sources/`、`index.md` 和 `log.md` 属于**综合层**，由 LLM 按本协议维护。
- 普通查询和健康检查默认只读。只有用户要求摄取、沉淀、修复或更新 Wiki 时才写文件。
- 不直接读写 CoreStudio 用户项目数据；项目上下文和写回应走 CoreStudio CLI / Local Bridge。

## 2. 来源优先级

不同来源描述冲突时，按具体问题选择最接近真实行为的证据，并保留冲突：

1. 用户当前明确确认的目标、范围和决策。
2. 当前代码、测试、运行配置和可复现的实时证据。
3. 标明为当前事实来源的稳定文档与正式 contract。
4. 已确认、已实现的 spec / plan。
5. 普通说明文档、历史计划、历史审计和发布记录。
6. Wiki 综合页。
7. 外部资料、研究和 LLM 推断。

版本号、分支、安装包、运行进程、端口、CI、发布和凭据等会漂移的信息，回答当前状态前必须重新验证，不能只引用 Wiki。

## 3. 证据状态

关键结论使用以下小写英文状态；状态描述的是**结论**，不是整个文件：

| 状态 | 含义 | 使用条件 |
| --- | --- | --- |
| `confirmed` | 已确认 | 有当前代码、测试、稳定文档或用户决策直接支持 |
| `proposal` | 提案 | 来自尚未完成或未确认的 spec、plan、设计稿或路线想法 |
| `observation` | 观察 | 来自一次审计、运行、日志或界面现象，尚未上升为稳定规则 |
| `inference` | 推断 | 由多个事实合理推导，但来源没有直接陈述 |
| `unknown` | 未知 | 当前来源不足、互相冲突或需要实时核验 |

写法示例：

```md
- `confirmed`：外部图片写回必须经过 CLI / Local Bridge。
- `proposal`：某历史计划提出未来增加某能力，但当前代码尚未确认。
```

禁止把以下内容静默提升为 `confirmed`：

- 历史计划中的目标状态；
- 设计稿和原型中可见但代码未实现的能力；
- 测试名称暗示但测试正文未证明的行为；
- 旧版本发布记录；
- 外部竞品或研究材料；
- LLM 根据目录名、分支名或版本号作出的推断。

## 4. 页面格式

主题页使用以下 frontmatter：

```yaml
---
title: 页面标题
type: product | architecture | workflow | engineering | design | reference | source
updated: YYYY-MM-DD
source_count: 1
---
```

正文至少包含：

1. 一段说明页面回答什么问题；
2. 当前结论，并对关键结论标注证据状态；
3. 与其他 Wiki 页的交叉链接；
4. `## 主要来源`，链接到仓库来源或来源说明；
5. 必要时增加 `## 冲突与未知`。

页面命名使用稳定、可预测的英文 kebab-case。中文标题写在 frontmatter 和一级标题中。

## 5. 新建页还是更新旧页

- 新信息是现有实体、概念或工作流的属性和变化时，更新现有页。
- 只有当一个概念能被多个页面独立引用、拥有独立来源集合，并且不能自然归入现有页时才新建页。
- 新建前必须搜索 `index.md`、页面标题、别名和关键术语，避免近义重复页。
- 一个主题只保留一个主页面；历史变化写入同页或来源文档，不以日期复制整页。

## 6. 摄取流程

1. 先读 `index.md`、相关主题页和 `sources/source-map.md`。
2. 判断来源类型、时间、适用版本、权威程度和是否可变。
3. 提取原文直接支持的结论；分别记录冲突、未知和推断。
4. 更新所有受影响的主题页和交叉链接，不只新建一篇来源摘要。
5. 新页面加入 `index.md`；新增来源加入 `sources/source-map.md`。
6. 在 `log.md` 追加一条 `ingest` 记录。
7. 检查相对链接、索引覆盖和 Git diff，确认没有改到来源层。

## 7. 查询流程

1. 从 `index.md` 找主题页。
2. 读取主题页的主要来源；高风险或易漂移结论直接核对当前代码或运行状态。
3. 回答中区分已确认、提案、观察、推断和未知。
4. 给出仓库相对路径，不能只说“文档里写了”。
5. 查询本身不写 Wiki；用户要求沉淀时，再按摄取流程更新。

## 8. 体检流程

体检至少检查：

- Markdown 相对链接是否存在；
- `index.md` 是否覆盖所有主题页和入口页；
- 是否有孤立页面或同义重复页面；
- `confirmed` 结论是否缺少直接来源；
- 历史 plan / spec 是否被误写成当前事实；
- 页面间是否存在未解释的冲突；
- 版本、分支、端口、支持模型和发布状态是否已经漂移；
- 重要来源是否新增但尚未摄取；
- `log.md` 是否保持追加式记录。

体检默认输出问题清单，不自动改动。修复时只改 Wiki 综合层。

## 9. 冲突处理

- 不覆盖旧证据来制造“一致”。
- 记录每个说法的来源、日期、适用范围和状态。
- 当前代码与旧文档冲突时，把当前行为写为 `confirmed`，把旧文档标为历史或待更新来源。
- 无法判定时使用 `unknown`，并写出最小验证办法。
- 产品取舍和范围边界冲突必须交给用户确认，不由 Wiki 维护者自行决定。

## 10. 日志规则

`log.md` 是追加式时间线。每条记录以可解析标题开头：

```md
## [YYYY-MM-DD] ingest | 来源或主题
## [YYYY-MM-DD] query | 问题摘要
## [YYYY-MM-DD] lint | 检查范围
```

日志只记知识库发生了什么，不复制长篇结论；详情链接到相关页面。
